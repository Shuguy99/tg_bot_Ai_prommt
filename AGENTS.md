Правила проекта для AI-агентов (opencode). Файл читается автоматически при старте сессии.

## Текущее состояние репозитория

Зафиксировано на момент создания файла. **Перед планированием работ проверь, не устарело ли это.**

- Репозиторий инициализирован (`git init`), **коммитов ещё нет**.
- Единственная директория — `tgbot/` (пустая). Исходного кода нет.
- Стек, зависимости, сборка, тесты и CI **ещё не выбраны**. Не предполагай наличие
  `package.json`, `requirements.txt`, линтеров или тест-раннеров — сначала проверь
  (`ls`, `glob`), потом действуй.

Из этого следует главное правило:

> **Не выдумывай архитектуру.** Если фича не описана и кода нет — задай уточняющий
> вопрос или предложи план с явной оговоркой об отсутствующих предпосылках.
> Любое решение, зафиксированное в этом файле, помечай как «принято» и датируй.

## Правила работы

1. **Читай перед правкой.** Найди соседние файлы и следуй их стилю. Не вводи новую
   библиотеку, не проверив, что она уже используется в проекте.
2. **Минимальный диff.** Одна задача — один логически связный коммит. Не смешивай
   рефакторинг с новой функциональностью.
3. **Коммит только по явной просьбе.** Никогда не запускай `git commit` / `push` /
   `gh pr create` сам. Перед коммитом покажи `git status` и `git diff`.
4. **Комментарии в коде — только по требованию пользователя.** Код должен читаться
   сам. Исключение: короткий `why`-комментарий, если поведение неочевиден.
5. **Не оставляй мусор:** debug-логи, закомментированный код, `TODO` без владельца,
   лишние зависимости. Перед завершением прогони линтер/тесты, если они есть.

## Безопасное использование инструментов

### Границы файловой системы

- Работай **только внутри рабочей директории** проекта.
- Любое обращение за её пределы (`~`, `/etc`, `/usr`, другие проекты) — только по
  явному разрешению пользователя.
- **Удаление файлов (`rm`, `rm -r`, `git clean`, `trash`) — всегда с подтверждением.**
  Перед удалением покажи, что именно удаляется, и дождись подтверждения.
- Не редактируй `~/.config/opencode/` и другие глобальные конфиги без прямой просьбы.
- Не трогай `~/.ssh`, `~/.aws`, `~/.gnupg`, `.env` — только чтение, и то по запросу.

### Сеть и Bash

- **Глобальные/необратимые сетевые команды — с подтверждением:** `curl | bash`,
  `wget` во внешние пути, `npm install -g`, `pip install --user`, запись в
  `/usr/local`, изменение системных сервисов.
- Установка пакетов фиксируй в файле манифеста проекта, а не глобально.
- Не выводи в логи и не коммить секреты. Токены передавай через переменные окружения
  или `{env:VAR}`-интерполяцию в конфиге.

### Секреты

- Никогда не хардкодь токены/ключи в исходники, конфиги или `AGENTS.md`.
- Если интеграции нужен токен (GitHub, API-ключи) — **остановись и запроси его у
  пользователя**, не пытаясь обойти авторизацию.
- Файлы с секретами добавляй в `.gitignore` до первого коммита.

## Конфигурация opencode

- Глобальный конфиг: `~/.config/opencode/opencode.jsonc` (именно `.jsonc`).
  Проектного `opencode.json` в репозитории нет.
- Схема: <https://opencode.ai/config.json>. opencode **не стартует** при невалидном
  конфиге, а unknown top-level ключи отвергает (`ConfigInvalidError`).
- Ключ секции MCP — **`mcp`**, а **не** `mcpServers` (последнего нет в схеме).
  Каждый сервер: обязательные `type` (`local`|`remote`) и `command`/`url`.
  `command` — **массив строк**.
- Конфиг читается один раз при старте и **не перечитывается на горячую**. После правки
  нужно перезапустить opencode.
- Проверяй правку до перезапуска, например:
  `jq empty ~/.config/opencode/opencode.jsonc`

### Права доступа (текущая политика)

- `bash`, `edit` (покрывает `write` и `apply_patch`) — работа в пределах рабочей
  директории.
- Удаление файлов и глобальные сетевые команды — `ask`.
- Порядок правил важен: opencode применяет **последнее** совпавшее правило, поэтому
  широкие шаблоны идут первыми, узкие — последними.
- Отдельных permission-ключей `write` / `apply_patch` не существует; файловые
  операции регулируются ключом `edit`.
